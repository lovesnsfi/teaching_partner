# 2026-10-09
- **排查「推送tag 后 GitHub Actions 没有产出 exe」**：根因是**版本号提交晚于 tag**。`v0.2.3` tag 指向 `f0b63b1`，而该提交里 `package.json.version` 仍是 `0.2.2`；electron-builder 是按 **package.json 的 version** 决定发布到哪个 Release（`tag → v${version}`），完全不看 git tag，于是产物被传到了已存在的 `v0.2.2` Release。用户看到的「只有 Source code (zip)」的 Release 是 GitHub 推 tag 时自动创建的，产物压根没进去。
  - 已在 `.github/workflows/build.yml` 的 Checkout 之后加 `Verify tag matches package.json version` 步骤：比对 `$env:GITHUB_REF_NAME` 与 `package.json.version`，不一致立即 `exit 1` 并输出中文错误，避免静默跑偏一整轮构建。
  - **正确发布顺序（务必记牢）**：改版本号 → 提交 → 在该提交上打 tag → 推送 tag。即"先 commit 再 tag"，tag 必须指向 version 已改好的那个提交。
  - 推送前自查：`git show v0.2.3:package.json | grep version` 必须等于 tag 版本号。
  - 待办：`v0.2.3` tag 需强制重指向到 `ac5a3d4`（版本号提交）并 `git push origin v0.2.3 --force`，已向用户确认待执行。
  - **补充：发布是否需要 `git push origin dev`？** 技术上不需要 —— 推 tag 会把所指提交对象一并传上，CI 按 tag checkout 能正常构建发布。但**应该推**，否则远端 `dev` 分支落后、本地与仓库状态不一致，别人 clone 拿不到发布内容。推荐顺序为 5 步：改版本号 → commit → **push 分支** → 打 tag → 推 tag。先推分支再打 tag 的理由：分支推送失败时 tag 还没打、CI 未触发，可从容处理；反过来则可能要回滚 tag。
- **新增 `release.bat` 一键发布脚本**（与 `pack-admin.bat` 配套）。用法 `release.bat [patch|minor|major|版本号]`，默认 patch。流程：检查 git/node/非 detached HEAD → **要求工作区干净**（否则 tag 会指向不完整代码）→ `npm version <bump> --no-git-tag-version` → 提交版本号 → 三重自检（本地无同名 tag / 远端无同名 tag / **校验 HEAD 中 package.json 版本 == tag 版本**）→ 打 tag 并校验指向最新提交（不符则自动 `git tag -d` 回滚）→ **先推分支后推 tag**。任何一步失败都跳到 `:fail` 且**不推送任何内容**。开头 `chcp 65001` 保证中文输出不乱码；用 `cd /d "%~dp0"` 定位自身目录。
  - 核心自检用 `git show HEAD:package.json | node -p "require('fs').readFileSync(0,'utf8')"` 读版本（已实测可行）。

  - 新增统一入口 `runCheck() = pickAvailableFeed() → autoUpdater.checkForUpdates()`，**三个调用点全部改走它**：启动 10s 后的自动检查、`updater:check` IPC、以及 error 事件里的「切源后重试」。这样镜像不通到切到 GitHub 只需 ~4 秒，而不是等一次长超时（electron-updater 本身没有可配的请求超时）。
